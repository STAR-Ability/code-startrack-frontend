# codeStartrack V0.1 Frontend Execution Plan

Planning completed: 2026-09-30; amended the same day for the explicitly approved server-side GET gateway and Docker deployment. Application implementation has not started.

## Goal

Demonstrate one unified codeStartrack training profile and one source-aware recommendation for the existing Demo learner, using only the live backend's permitted GET reads. A learner can review supported metrics, understand the recommendation's placeholder limitation, and open the returned external problem URL.

The approved product journey remains connection → account synchronization → unified profile → recommendation. This development phase demonstrates only existing data → profile → recommendation → external link. Completion of that slice must not be described as completion of live account binding, synchronization, or multiple same-platform accounts.

### Approved server-side API boundary

```text
Browser (same-origin API requests)
  → Next.js frontend Route Handlers
  → server-only GET backend client using runtime BACKEND_BASE_URL
  → existing backend E1/E2 for DEMO_USER_ID = 1
```

| Frontend-owned technical endpoint  | Only permitted upstream operation          |
| ---------------------------------- | ------------------------------------------ |
| `GET /api/training/profile`        | `GET /api/users/1/profile`                 |
| `GET /api/training/recommendation` | `GET /api/users/1/recommendations?limit=1` |

These two frontend routes are newly planned implementation boundaries, not invented backend APIs or additional product pages. Browser code uses relative same-origin URLs and receives only validated data/safe normalized errors. Keep `BACKEND_BASE_URL` and the backend client behind `server-only` imports. Browser data fetching must never contact the backend directly; the approved user-clicked external problem CTA remains ordinary external navigation.

Use two explicit Node.js Route Handlers, not a catch-all proxy. Fix the learner and query server-side; reject unexpected query/body inputs locally. Do not accept client-selected host, URL, path, user ID or limit, and do not forward cookies, credentials, client headers or method overrides. The private transport constructs only the two allowlisted GET requests, with bounded timeout, no automatic retry, `redirect: error` and no-store behavior. Do not fetch during build/import, opt these handlers into static caching, or expose a public runtime-configuration endpoint.

POST/PUT/PATCH/DELETE and all other non-GET gateway methods must produce zero upstream requests. Unsupported methods return a local 405; explicitly handle HEAD locally because the installed Next.js auto-implementation otherwise calls GET. OPTIONS can return a local framework response, but must never call the backend. Test these against the local gateway and a controlled upstream stub, never by sending prohibited requests to the live backend.

Keep documented upstream status/error semantics separate from the frontend-owned error contract. Preserve available upstream HTTP status and safe machine identifiers; map transport/timeout/invalid-payload/configuration errors deliberately at the gateway, and never serialize stack traces, raw backend bodies, host addresses or environment values to the browser. Record the frontend mapping in V01-01 without inventing upstream error identifiers.

An HTTPS browser now talks only to its HTTPS Next.js origin; server-to-server HTTP is outside browser CORS and mixed-content enforcement. This does not encrypt that server-to-server hop or demonstrate container connectivity. Do not enable `no-cors`, disable browser security, expose the backend through `NEXT_PUBLIC_*`, or hardcode its IP in application/container source.

## Product Constraints

- One internal learner can have zero or more external accounts; the target permits repeated platform names. Each account has its own backend identity and sync operation. The backend owns normalization, deduplication and unified metrics.
- Codeforces is the only working connector. Platforms are source metadata, never modes, learner identities, selected-account profiles, or separate dashboards.
- Only `/` and `/dashboard` are primary product routes. No locale-prefixed product routes are required.
- Preserve white-first Base UI/Nova, Geist/Geist Mono and Lucide. P-05 color selection is resolved: reuse the exact white/neutral-first semantic palette (near-black primary; blue accent only) in the product design document; application of tokens remains V01-03. One recommendation is the strongest action; no dense dashboard, radar or decorative illustration work.
- Show only genuinely known accounts. E1/E2 do not disclose account IDs or handles; neither missing local state nor a 404 proves an empty account collection.
- `skills` is placeholder data; do not render measured ability. Recommendations and their reasons are placeholders; do not reinterpret `score` as confidence or strengthen personal claims.

- `DEMO_USER_ID = 1` is resolved for V0.1 (G-01). Introduce one replaceable configuration export; route components must not scatter literal IDs or substitute external handles/account IDs.
- The internal user already exists. Do not add registration, login, authentication, sessions, provisioning or backend identity changes.

## Scope

### In Scope

- Server-only runtime environment/Demo configuration, a narrow GET client under `src/lib/api/`, two explicit Next.js gateway Route Handlers, Zod response validation and normalized safe errors.
- A small bilingual copy layer (`zh-CN` default, `en` supported) without duplicating the two-page route model.
- `/dashboard`: supported user metrics, distinct update/generation timestamps, one recommendation, placeholder disclosure and a source-aware external CTA.
- `/`: read-only onboarding/connected-account explanation and navigation to the existing Demo data. A visually represented handle form must be explicitly unavailable and have no submission handler that reaches the backend. No simulated connected row or progress sequence.
- Loading, zero/empty, error, partial-success, recovery, mobile and keyboard states for those reads.
- Offline tests through a controlled upstream stub and a separately invoked GET-only deployed integration check.
- Next.js standalone output, multi-stage Dockerfile, `.dockerignore`, `docker-compose.yml`, neutral `.env.example`, runtime configuration, production Node server, `restart: unless-stopped`, local healthcheck and a repeatable one-command Compose deployment. Operator and future capability tracking remain separate.

### Out of Scope

Registration, authentication and full sessions; internal editor/problem workspace; Run Sample; internal Judge/submission and AC/WA/TLE/CE/RE flows; progressive or real LLM Agent assistance; coach/team/role experiences; platform dashboards; additional real connectors; radar/large analytics; RAG/vector databases/AI-generated problems; community, leaderboard and payments. No backend edits, invented APIs, extra internal users, browser profile merging, real multi-account binding, unbind/replace/remove, open-ended proxying, public backend configuration or browser-security bypasses. The explicitly approved narrow GET gateway and Docker deployment are in scope; automated GHCR publishing and production TLS/domain provisioning require their own operational setup.

E3/E4/E5 activation is deferred by the read-only policy even though it is documented product/operator behavior. Planning their future boundaries is not authorization to implement or execute them now.

- [ ] Every live request is a permitted GET; no mutation implementation is activated by these stages.
- [ ] Both locales cover visible copy, metadata, state messages and accessible names under the approved P decisions.
- [ ] Profile/recommendation show real returned values, separate timestamps, truthful limitations and a safe source URL.
- [ ] Missing account context, zero activity, empty recommendations, errors and partial success remain distinct.
- [ ] Tests have no live dependency or data mutation, and normal checks plus major-flow E2E pass.
- [ ] Browser API requests are same-origin; the two fixed gateway handlers forward only approved GETs. Unsupported methods/inputs trigger zero upstream requests.
- [ ] `docker compose up -d` runs the production standalone Node server with runtime configuration, restart policy and local healthcheck; the same image works with two runtime base URLs without rebuilding browser JavaScript.
- [ ] Live browser → Next.js → backend evidence is recorded separately in V01-09; historical direct-browser CORS failure is not a remaining architecture decision.
- [ ] Product/API gaps and deferred operations remain visible; no identity/backend feature change is required for the first frontend Issue.

## Testing

- Unit: configuration failures without a localhost/live fallback; safe IDs; exact GET paths and `limit=1`; JSON/schema parsing; finite numeric values; optional display metadata; unknown error body and ambiguous 404; abort/network errors; external URL validation. Use injected/stubbed fetch and synthetic fixtures, never saved live learner payloads.
- Component/integration: Query provider and isolated cache; profile pending/success/zero/error; recommendation pending/empty/error; profile retention on E2 failure; unavailable external CTA; read-only onboarding keyboard submission; locale key parity, formatting and unknown account context. No generic rebind recovery.
- Gateway integration: start the real Next.js server against an isolated synthetic HTTP upstream via runtime BACKEND_BASE_URL. Assert only the two exact upstream GETs; exercise local POST/PUT/PATCH/DELETE/HEAD/OPTIONS and invalid-query/destination attempts with zero upstream requests. Never test prohibited methods against the live backend. Browser route interception cannot replace this server-side test boundary.
- E2E: reuse desktop Chromium and Pixel 7. Build without backend configuration; inject only the controlled upstream URL at server startup, overriding any local live env. Exercise `/` → `/dashboard`, reload, both locales, partial success and responsive/keyboard behavior through the real gateway. Audit both browser same-origin requests and server/stub traffic; reject unexpected egress and block service workers. Component-only browser fixtures remain test-only and are not counted as gateway coverage. Verify the external CTA without depending on the third-party site.
- Docker: test Compose config, production startup/health, standalone static files, local env exclusion, same-image runtime retargeting and browser → gateway → stub flow with normal browser security. Healthchecks must never read the upstream backend.
- Live smoke: separately invoked against the deployed Next.js origin; the browser calls its two gateway GETs and only the server contacts the configured live backend. Audit both hops and distinguish actual status/data errors from transport failures. No retries, direct-browser fallback, catalogue/bind/sync setup or data repair. Diagnostic response headers/bodies must not disclose the upstream address.
- Build/type/lint: run `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm build`; run `pnpm test:e2e` for the major flows. Build without a backend value; runtime test BACKEND_BASE_URL must point to the controlled stub and override local live settings. No test may accidentally inherit a live destination. Existing Google-font build requests may need network permission and are separate from backend reads.

## Risks

- The approved server-only gateway removes direct-browser CORS and HTTPS-to-HTTP mixed-content dependency, but container egress, upstream availability/timeouts and actual deployed behavior remain unverified until V01-08/09. Server-to-server traffic to the current backend remains HTTP.
- Successful sample payloads do not resolve G-03/G-04/G-06/G-08. Strict validation may reveal further backend inconsistencies; do not mask them as empty success or relax the contract silently.
- Placeholder recommendation reasons can sound personalized. The limitation must remain near the reason/CTA in both locales; backend-provided prose is not automatically translated.
- Shared Demo data can change independently. No test asserts fixed real counts/problem IDs, and no frontend call repairs data.
- P-01–P-05 are resolved. A clean integration baseline and final bilingual copy/detail review must precede UI PR acceptance; ordinary `git diff` alone is insufficient while preparing the untracked scaffold baseline.
- Runtime configuration can be accidentally baked in or leaked through shared imports/errors/env-file copies. Verify server-only imports, no-store request-time behavior, neutral builds and two-runtime same-image tests. Compose `.env` interpolation alone does not inject a variable into the container; pass it explicitly.

## Rollback / Reversibility

Merge small Issue branches into `dev` through reviewed PRs; never push directly to `dev` or `main`. Revert only the affected PR, respecting dependent PRs. Do not reset the user's pre-existing uncommitted files. The first Issue leaves both product pages unchanged, adds only the two technical gateway routes and no backend writes, so rollback has no data migration. Roll back Docker releases by restoring the previous immutable image reference and recreating the service with its runtime configuration; never revert to public backend configuration or enable mutations.

Replace the single Demo configuration export with a future identity source only under a separately approved task. Keep user ID and external account ID distinct so that replacement does not require rewriting components. The environment URL, API accessors, Zod schemas, query region and copy dictionaries remain separable. Future account discovery/mutations can extend the same user-level experience after contracts and authorization exist; do not ship dormant mutation toggles now.
