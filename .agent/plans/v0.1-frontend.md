Planning completed: 2026-09-30; amended the same day for the explicitly approved server-side GET gateway and Docker deployment. V01-01 is now merged into `dev`; V01-02 details are accepted under the user’s delegated decision authority; V01-03–07 are complete; V01-08 is next.

## Goal

Demonstrate one unified codeStartrack training profile and one source-aware recommendation for the existing Demo learner, using only the live backend's permitted GET reads. A learner can review supported metrics, understand the recommendation's placeholder limitation, and open the returned external problem URL.

The approved product journey remains connection → account synchronization → unified profile → recommendation. This development phase demonstrates only existing data → profile → recommendation → external link. Completion of that slice must not be described as completion of live account binding, synchronization, or multiple same-platform accounts.

### Approved server-side API boundary

```text
Browser (same-origin API requests)
  → Next.js frontend Route Handlers
  → server-only GET backend client using runtime BACKEND_BASE_URL
  → existing backend E1/E2 for DEMO_USER_ID = 1
```

| Frontend-owned technical endpoint  | Only permitted upstream operation          |
| ---------------------------------- | ------------------------------------------ |
| `GET /api/training/profile`        | `GET /api/users/1/profile`                 |
| `GET /api/training/recommendation` | `GET /api/users/1/recommendations?limit=1` |

These two frontend routes are newly planned implementation boundaries, not invented backend APIs or additional product pages. Browser code uses relative same-origin URLs and receives only validated data/safe normalized errors. Keep `BACKEND_BASE_URL` and the backend client behind `server-only` imports. Browser data fetching must never contact the backend directly; the approved user-clicked external problem CTA remains ordinary external navigation.

Use two explicit Node.js Route Handlers, not a catch-all proxy. Fix the learner and query server-side; reject unexpected query/body inputs locally. Do not accept client-selected host, URL, path, user ID or limit, and do not forward cookies, credentials, client headers or method overrides. The private transport constructs only the two allowlisted GET requests, with bounded timeout, no automatic retry, `redirect: manual` (reject redirects without following them) and no-store behavior. Do not fetch during build/import, opt these handlers into static caching, or expose a public runtime-configuration endpoint.

POST/PUT/PATCH/DELETE and all other non-GET gateway methods must produce zero upstream requests. Unsupported methods return a local 405; explicitly handle HEAD locally because the installed Next.js auto-implementation otherwise calls GET. OPTIONS can return a local framework response, but must never call the backend. Test these against the local gateway and a controlled upstream stub, never by sending prohibited requests to the live backend.

Keep documented upstream status/error semantics separate from the frontend-owned error contract. Preserve available upstream HTTP status and safe machine identifiers; map transport/timeout/invalid-payload/configuration errors deliberately at the gateway, and never serialize stack traces, raw backend bodies, host addresses or environment values to the browser. Record the frontend mapping in V01-01 without inventing upstream error identifiers.

An HTTPS browser now talks only to its HTTPS Next.js origin; server-to-server HTTP is outside browser CORS and mixed-content enforcement. This does not encrypt that server-to-server hop or demonstrate container connectivity. Do not enable `no-cors`, disable browser security, expose the backend through `NEXT_PUBLIC_*`, or hardcode its IP in application/container source.

## Product Constraints

- One internal learner can have zero or more external accounts; the target permits repeated platform names. Each account has its own backend identity and sync operation. The backend owns normalization, deduplication and unified metrics.
- Codeforces is the only working connector. Platforms are source metadata, never modes, learner identities, selected-account profiles, or separate dashboards.
- Only `/` and `/dashboard` are primary product routes. No locale-prefixed product routes are required.
- Preserve white-first Base UI/Nova, Geist/Geist Mono and Lucide. P-05 color selection is resolved: reuse the exact white/neutral-first semantic palette (near-black primary; blue accent only) in the product design document; application of tokens remains V01-03. One recommendation is the strongest action; no dense dashboard, radar or decorative illustration work.
- Show only genuinely known accounts. E1/E2 do not disclose account IDs or handles; neither missing local state nor a 404 proves an empty account collection.
- `skills` is placeholder data; do not render measured ability. Recommendations and their reasons are placeholders; do not reinterpret `score` as confidence or strengthen personal claims.

## Scope

### In Scope

- Server-only runtime environment/Demo configuration, a narrow GET client under `src/lib/api/`, two explicit Next.js gateway Route Handlers, Zod response validation and normalized safe errors.
- A small bilingual copy layer (`zh-CN` default, `en` supported) without duplicating the two-page route model.
- `/dashboard`: supported user metrics, distinct update/generation timestamps, one recommendation, placeholder disclosure and a source-aware external CTA.

- Loading, zero/empty, error, partial-success, recovery, mobile and keyboard states for those reads.
- Offline tests through a controlled upstream stub and a separately invoked GET-only deployed integration check.
- Next.js standalone output, multi-stage Dockerfile, `.dockerignore`, `docker-compose.yml`, neutral `.env.example`, runtime configuration, production Node server, `restart: unless-stopped`, local healthcheck and a repeatable one-command Compose deployment. Operator and future capability tracking remain separate.

### Out of Scope

Registration, authentication and full sessions; internal editor/problem workspace; Run Sample; internal Judge/submission and AC/WA/TLE/CE/RE flows; progressive or real LLM Agent assistance; coach/team/role experiences; platform dashboards; additional real connectors; radar/large analytics; RAG/vector databases/AI-generated problems; community, leaderboard and payments. No backend edits, invented APIs, extra internal users, browser profile merging, real multi-account binding, unbind/replace/remove, open-ended proxying, public backend configuration or browser-security bypasses. The explicitly approved narrow GET gateway and Docker deployment are in scope; automated GHCR publishing and production TLS/domain provisioning require their own operational setup.

E3/E4/E5 activation is deferred by the read-only policy even though it is documented product/operator behavior. Planning their future boundaries is not authorization to implement or execute them now.
