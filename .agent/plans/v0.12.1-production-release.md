## Implementation Stages

### Stage 1 - Prepare and merge

Confirm branch ancestry, prepare patch metadata on dev, safely update main, and use the existing non-fast-forward merge convention. Run pnpm check, Storybook build/tests and complete E2E from merged main; review before push.

### Stage 2 - Publish

Wait for main CI, dispatch release.yml on the verified main SHA, and verify immutable version/commit tags, digest, OCI revision and exact-image acceptance. Use the existing Actions registry authentication.

### Stage 3 - Deploy

Reinspect the frontend, save restricted release configuration/container metadata, create a new version directory, copy only production Compose, pull the pinned image and run up --no-build --no-deps -d --wait frontend with the existing project name. Preserve the old image and release directory.

### Stage 4 - Verify and record

Verify container health/logs/ports, unchanged backend identity, ingress/API routing, real public browser flows, assets and no Mock interception. Record receipt; restore the old frontend on a critical release regression.

Keep the actual previous image, release files and restricted metadata backup. If startup or critical smoke fails, recreate only frontend using the previous release's pinned Compose/env, then verify health/pages/API. Never restart backend or remove volumes/unrelated containers.
