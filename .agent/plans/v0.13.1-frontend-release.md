# V0.13.1 integration, ten refinement rounds, and production release

## Goal

Render structurally valid evolving algorithm responses, improve the existing
learning workspace through ten accepted rounds, and release the verified frontend
from dev through main and GHCR to startrack-prod.

## Implementation Stages

Each stage starts with an Issue containing scope, owner, acceptance and checks.
Root owns architecture, review, acceptance, GitHub and production operations.

1. **Contract audit:** integration subagent inspects loopback-tunnel OpenAPI and
   safe responses; remove algorithm literal coupling without weakening structure.
2. **Data reliability:** integration and QA address proven drift, compatibility
   presentation and regression fixtures, including malformed and future versions.
3. **Surface hierarchy:** design subagent refines shared tokens and semantic
   surfaces, preserving fixed decoration and readable primary content.
4. **Profile and analysis:** redesign conclusion, metrics, abilities, source
   context, evidence and history while retaining all actions and frozen data.
5. **Recommendations:** make ranked problem, reason, ability and next action
   primary; preserve generation, modes, history and completion semantics.
6. **Dashboard and navigation:** refine overview hierarchy and navigation density.
7. **Teams, coach and accounts:** align secondary areas and role-aware actions.
8. **Visualization and motion:** polish chart grammar, tooltips, labels, legend,
   accessible evidence and reduced-motion behavior.
9. **Responsive, accessibility and states:** QA exercises real dimensions,
   translations, keyboard and loading/empty/error scenarios; fix actual defects.
10. **Final design review:** root reviews rendered product and full diff, resolves
    inconsistencies, updates release metadata and runs final acceptance suites.

## Testing

- Unit/integration: actual pnpm test scripts plus targeted API and component tests.
- Browser: built mock harness, Playwright MCP screenshots and executable E2E.
- Stories: production component stories, build-storybook and test:storybook.
- Quality: lint, format:check, typecheck, production build and container checks.
- Live: unauthenticated contract and session checks; authenticated GET checks only
  when a designated test session is available. Never recover private sessions
  from server storage or represent mock evidence as authenticated live acceptance.
- Release: required PR CI, main CI, existing main-only release workflow, image
  revision/digest, Compose canary/health/assets/proxy and production browser checks.

## Risks

- Historical contract metadata may differ from running algorithms.
- Authenticated production acceptance has no designated session. The user approved
  mock/E2E coverage plus live contract/unauthenticated checks and an explicit
  not-directly-validated limitation; this does not block release.
- Static export requires query-driven resource routes and same-origin proxy.
- Translucent surfaces must keep text contrast and avoid expensive blur.
- Shared workspace changes affect multiple routes and Storybook consumers.
- GHCR version tags cannot be overwritten; release metadata must be bumped.

## Rollback / Reversibility

Preserve the current production Compose/env and image digest in a restricted server
backup. Pull and validate the immutable replacement before touching the running
frontend. Replace only the frontend service; restore the previous Compose/image
if health or integration fails. Do not change backend services, volumes or ingress.
