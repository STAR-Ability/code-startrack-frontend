# codeStartrack frontend design audit

Audit date: **2026-10-07, Asia/Shanghai**. Baseline: `dev` at `c3aba367672d6719f802a8c2f0023f5e40897daf`, package 0.13.3. The initial worktree contained a user modification to `.gitignore`; it is preserved. This task changes documentation only. No production UI, library, dependency, backend contract, live data, credential, deployment or Git history is modified.

## 1. Design director's assessment

codeStartrack already has a credible foundation: source-owned Base UI/Nova primitives, restrained Geist/CJK typography, semantic blue/violet/teal accents, layered surfaces, accurate analytical views and extensive synthetic behavior tests. It is not an unmodified shadcn dashboard, and the workspace is not a flat white canvas. Replacing the foundation would discard useful accessibility and data-state work.

The largest opportunity is **composition and task clarity**. The interface repeatedly gives secondary context the same boxed prominence as primary evidence. Desktop submission filters and cards waste comparison space; mobile practice places an existing result below substantial chrome; some passive cards lift as though clickable. Public capability claims contradict the current documented contract. Feedback is structurally robust but can duplicate loading/error surfaces and does not consistently explain local validation failures.

The target is a deliberately composed training instrument: clear next action, exact evidence, quieter context/history, a recognizable orbit/trajectory identity, and the same visual language across public pages, authentication and application workspaces. See [the blueprint](frontend-redesign-blueprint.md) for the concrete system and [the execution prompt](../../prompts/frontend-visual-overhaul.md) for implementation.

## 2. Evidence method and limits

Specialists independently inspected architecture/product contracts, design tokens/shared components, accessibility/motion/performance, UI ecosystem source and licenses, skills/provenance, and rendered browser behavior. CodeGraph preceded code discovery; current files and executed browser/command output remained authoritative.

The application was built and served using `pnpm preview:offline`: static frontend on loopback 3100, synthetic service on loopback 3210. `tests/gateway-server.mjs` overrides the backend origin, so local private environment configuration was not used to choose a live upstream. Browser requests were monitored; fixture state changes were coordinated. No live authentication or write was attempted.

Evidence labels in this report:

- **Rendered:** an actual browser image, interaction or geometry measurement reviewed during this audit.
- **Source:** current code/configuration establishes structure or a potential failure; it is not proof of a visible defect.
- **Contract/document conflict:** current designated sources disagree with presentation text; it does not establish service availability now.
- **External dependency:** the current API does not provide a required capability; a frontend redesign cannot fabricate it.

Screenshots and runtime manifests are under ignored `test-results/design-audit/`. They are local audit artifacts, not committed visual baselines. The broad baseline captures 26 non-coach route entries × 5 widths (1440, 1280, 768, 390, 320) × 2 locales (zh-CN/en) = 260 screenshots. A further 206 entries cover coach routes, owner tabs, member domains and empty/error/loading/guest states, for **466 matrix captures**. All 29 routes have a capture at each width and locale. Desktop/mobile contact sheets were inspected for the 26 baseline entries, with full-size/viewport inspection of key pages and additional coach/states; selected laptop/tablet/320px English layouts were also viewed. Capturing a file is not equivalent to individually reviewing it: the audit does not claim every pixel of all 466 images was reviewed. Three prematurely settled captures were identified and recaptured before finalizing the manifests.

Full-page screenshots can show fixed shell decoration only in the initial viewport. A scrolled viewport inspection confirmed the workspace wash remains visible; whiteness below the first viewport in a long screenshot is not a layering defect.

Automated accessibility scans are partial evidence. Independent axe-core 4.13 scans of nine representative routes (`/`, `/login`, `/register`, `/dashboard`, `/practice`, `/profile`, `/data`, `/security/password`, `/teams`) at 1280px and 390px English reported no violations. Six route types (12 of 18 scans) had incomplete color-contrast analysis; login, registration and password-change samples had none. Manual keyboard, text sizing, reduced motion and contrast review remain necessary. This report does not claim full WCAG conformance or production/live-backend acceptance.

### Concrete visual interpretation

The landing hero has a clear left/right composition, restrained orbit and readable primary promise. The problem is lower-page repetition: five boxed process steps, four similarly boxed capability exhibits and another illustrative journey create a component-assembled rhythm. Refine it into connected process/evidence sections and keep one distinctive illustration. Avoid replacing a viable hero with an imported effect.

Dashboard and profile share semantic tokens and already prioritize a next-practice direction. The dashboard still stacks several broad evidence/metric/chart modules before compact report/team updates, while the profile's radar is small relative to its available column. Improve density and area allocation before changing colors. A sparse fixture is valid; retain supplied windows and do not fabricate additional activity for visual balance.

Recommendations already distinguish the featured first problem, matched dimensions, reason, action, remaining queue and history. Preserve that progress. The highest mobile issue is the volume of context and generation controls before an existing batch, not a need for more recommendation decorations. Team/settings pages require consistent task rows and readable form widths, not another hero on every route.

Extended owner/coach inspection adds the same hierarchy lesson: owner detail at 320px English repeats generic page identity, team identity and seven tabs wrapping roughly five lines before analytical content. Coach desktop has one team card next to five long activity/notification entries, leaving an avoidable large void in the shorter column. Compact context/tabs and support rows can improve these views while retaining all items, URL tab values, role/lifecycle guards and metadata. The member-view identity omission in F22 is a separate, higher-priority provenance concern.

### Existing strengths that constrain the redesign

- FormInput owns labels/descriptions/password visibility; shared focus-visible rules and real link/button semantics are widely present.
- Public native summary navigation and Base UI Sheet/dialog focus provide a good starting point. Independent keyboard skip-to-main, mobile Sheet focus containment and a follow-up Escape/trigger-return test passed. An earlier rapid-tab dismissal observation did not reproduce; it is a regression scenario, not a confirmed hidden-tooltip defect.
- Backend ranks, frozen snapshots, unknown versus true zero, profile order and version compatibility are handled deliberately. These are design assets, not friction to remove.
- ECharts uses actual SVG geometry, responsive resizing, browser-resolved CSS colors, reduced-motion handling and visible/disclosed exact values.
- Reading/support layers and shell decoration already form a common product language. Fine-tune their hierarchy; do not add arbitrary gradients/shadows/glass behind every module.
- Empty/error/read-only/auth states exist; refine their presentation rather than inventing fake success, live fallback fixtures or new onboarding routes.

## 6. Preservation checklist

The following are more consequential than any visual flourish:

1. Keep static export and existing route/deep-link query parameters.
2. Keep same-origin credentialed APIs, Zod DTO/envelope/identity checks, nonblocking unknown algorithm versions, decimal-string IDs and UUIDs.
3. Preserve private query scoping, cancellation, session clearing, account switching/unbinding and initiating-user mutation guards.
4. Preserve guest workspace/practice and existing applicable session/role/resource gates. Selected-account gates apply only to account-local operations; user/team/settings no-binding access remains. COACH is additive and does not bypass per-team `canManage`.
5. Personal aggregate is backend-owned; account selection does not change it. Current analysis, frozen reports and independently authorized member domains never merge.
6. Recommendations retain backend rank/order/modes/coverage/completion, explicit generation and idempotency, limits, cooldowns, polling and null-link behavior.
7. Preserve four privacy scopes and revocation; user/team/audience history caches remain distinct.
8. Retain CAPTCHA/email verification/expiry, existing password and username rules, logout and reauthentication.
9. Synthetic evidence remains explicit; failures never enable mock data. All validation mutations remain fixture-bound.
10. Existing locale architecture, formatting, dates/timezones and accessible values remain; no new i18n or chart system.

Exact contracts are distilled further in the blueprint and execution prompt; source remains authoritative if the worktree changes after the audit.
