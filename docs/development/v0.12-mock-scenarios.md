# V0.12 deterministic frontend scenarios

## One model, two isolated transports

`src/lib/demo/v012-fixtures.ts` contains DTO-typed baseline snapshots. `v012-scenarios.ts` supplies identity, collaboration, privacy, analysis and AI builders using the production DTO definitions. `src/lib/mock/v012-backend.mjs` owns synthetic transitions; `requests.mjs` validates the same request paths and fields used by the production adapters.

The local HTTP service uses this state machine for development, Vitest and Playwright. Storybook's `stories/mock/request-interceptor.ts` reuses the validator and state machine through a browser-only fetch transport. Storybook loaders install it only for stories with `parameters.mockScenario`, restore the previous transport between stories, and reject unhandled API requests locally. Production components and API adapters do not import or select Mock mode.

All collaboration entity IDs and mutation timestamps reset deterministically. Response request IDs are transport metadata. Synthetic data never comes from production learners, and a failed live request never activates a fixture. These scenarios simulate outcomes; they do not execute Algorithm, Codeforces, email or LLM services.

## Selecting a scenario

```bash
MOCK_SCENARIO=coach-owner-member pnpm dev:mock
# Or, after pnpm build:
MOCK_SCENARIO=team-no-level pnpm preview:mock
```

Development binds an available loopback fixture port and prints its control URL at startup. The launcher passes that origin directly to Next, overriding `BACKEND_BASE_URL` and `.env.local`; it never reuses another process's fixture. Set `MOCK_PORT` to an integer from 0 to 65535 to choose an explicit port (0 selects an available port). An occupied explicit port fails with a readable diagnostic before Next starts.

E2E and static preview own ports 3100/3210. Stop manual previews before `pnpm test:e2e`, and stop Next development before building because both use `.next`. Storybook uses its own in-browser state and does not require the HTTP service.

The loopback service exposes `/__control` directly at the printed fixture origin, outside the browser's `/api/v1` proxy. GET lists available scenarios and recorded calls. POST resets business state. For predictable control commands, select port 3210 explicitly after stopping any preview:

```bash
MOCK_PORT=3210 pnpm dev:mock
# In another terminal:
curl -sS http://127.0.0.1:3210/__control
curl -sS -X POST http://127.0.0.1:3210/__control \
  -H 'Content-Type: application/json' \
  -d '{"scenario":"applications-many"}'
```

The launcher closes its fixture when Next exits, cannot start, or is interrupted with Ctrl+C/SIGTERM. Refresh the frontend after resetting identity or business state. Tests use `configureUpstream({ scenario: "coach-owner-member" })`. Its optional `preserveCalls` merges fault/delay flags without resetting business state; it is intended for recovery/revocation tests, not identity switching.

## Scenario matrix

| Family               | Named scenarios / coverage                                                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| STUDENT              | `student`, `student-no-cf`, `student-one-cf`, `student-multiple-cf`                                                                                                                                                                    |
| STUDENT + COACH      | `coach-no-teams`, `coach-one-team`, `coach-multiple-teams`, `coach-owner-member` (owner A, member B)                                                                                                                                   |
| Lifecycle            | `team-active`, `team-archived`, `team-dissolved`; ACTIVE/LEFT/REMOVED memberships in builders                                                                                                                                          |
| Applications         | All PENDING/APPROVED/REJECTED/CANCELLED records; `applications-empty`, `applications-many` (25 pending); approval, rejection and cancellation transitions                                                                              |
| Invitations          | All PENDING/ACCEPTED/REJECTED/EXPIRED/CANCELLED records; registered and unregistered recipients; PENDING/SENT/FAILED delivery; `invitations-empty`, `invitations-delivery`, `owner-delivery-failed`; resend and rate-limit transitions |
| Member access        | `member-private`, `member-training`, `member-ability`, `member-submissions`, `member-reports`, `member-all`, `member-mixed`; `members-privacy-matrix` contains every combination                                                       |
| User analysis        | `user-no-analysis`, `user-one-source`, `student-multiple-cf`, `user-insufficient`, `stale`; all four windows, six dimensions and tag/difficulty/activity statistics                                                                    |
| Personal reports     | `no-report`, current + historical frozen snapshots, caution, generation success, `report-pending`, `report-running`, `report-failed-with-history`                                                                                      |
| Team analysis        | Both audiences; `team-no-analysis`, `team-no-ability`, `team-no-training`, `team-no-level`, `no-sharing`, `stale-coach`; sample-count invariants tested                                                                                |
| Team recommendations | Both audiences isolated by team; `team-no-recommendations`, `team-empty-recommendations`, `stale-coach`, `team-recommendations-running`, `team-recommendations-failed`                                                                 |
| AI jobs              | `ai-queued`, `ai-running`, `ai-success`, `ai-failed`; four statuses for USER_ANALYSIS, PERSONAL_REPORT, TEAM_ANALYSIS and TEAM_RECOMMENDATION; separate from CF SyncJob                                                                |
| Notifications        | Eight business types, structured references, mixed read state, `notifications-read`, `notifications-unread`, `notifications-empty`                                                                                                     |
| Failures             | `visitor`, `network-failure`, `server-error`, `members-server-error`; named `error-*` presets generated from `mockApiErrors`                                                                                                           |
| Loading              | `slow`, `slow-coach`; `delayMs` override                                                                                                                                                                                               |

`mockApiErrors` covers SESSION_EXPIRED, ROLE_REQUIRED, TEAM_FORBIDDEN, PRIVACY_DENIED, TEAM_ALREADY_MEMBER, TEAM_NOT_JOINABLE, APPLICATION_ALREADY_PENDING/PROCESSED, INVITATION_ALREADY_PENDING/PROCESSED/EXPIRED, TEAM_OWNER_CANNOT_LEAVE, USER_SOURCE_NOT_READY, USER_ANALYSIS_NOT_READY, TEAM_ANALYSIS_NOT_READY, TEAM_LEVEL_NOT_READY, TEAM_INVITE_RATE_LIMITED, REPORT_RATE_LIMITED and LLM_UNAVAILABLE. For example `error-team-forbidden` targets latest reads. Override `errorPath` or `errorResource` to target a specific operation. 429 responses include `Retry-After: 3`.

Builders ensure current owners are active members of non-dissolved teams, summary/detail references agree, active member counts exclude historical memberships, archive/dissolve cancel pending collaboration, and analysis counts satisfy the documented relationships. Member fixtures cannot read coach batches. Mock eligibility checks are contained in the synthetic service and never become frontend authorization rules.

## Documentation and verification

`Workspace/Collaboration` contains interactive team cards, owner overview, members, applications (pending/processed/empty/many), invitations/delivery failure, settings, coach/no-team dashboards, privacy, notifications, loading, error, archived, stale and restricted states. Existing `Workspace/V012` stories cover aggregate analysis, frozen reports, both analysis/recommendation audiences, zero samples and job/status families.

Run:

```bash
pnpm check
pnpm test:e2e
pnpm build-storybook
pnpm test:storybook
```

DTO/relationship tests are in `v012-scenarios.test.ts`; HTTP contract, lifecycle, AI, error and recovery tests are in `src/lib/mock/scenarios.test.ts` and `v012-backend.test.ts`. E2E verifies the same service, cache isolation, permission withdrawal, conflicts and cooldowns. Storybook checks enforce no actual backend requests and test local approval, keyboard Select and confirmation focus.

Live integration is a separate mode described in `v0.12-integration.md`. Passing these deterministic checks does not verify deployed authenticated permissions or real email/AI execution.
