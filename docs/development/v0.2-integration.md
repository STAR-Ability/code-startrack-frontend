# V0.2 frontend integration

## Contract and service boundary

The authoritative additive contract is release `0.2.0` in
[the V0.2 API](../../prompts/v0.2前端api文档.md),
[data reference](../../prompts/v0.2前端需要知道的数据库.md), and
[architecture](../../prompts/V0.2-整体架构与联调说明.md).
The audited delivery plan is
[v0.2-frontend-delivery.md](../../.agent/plans/v0.2-frontend-delivery.md).

Only the backend is reachable from browser API calls, through same-origin
`/api/v1/**` with the session cookie. Next App Router still exports static HTML;
nginx serves it on port 80, preserves API paths/Origin/Cookie, and uses a
30-second proxy request budget. Runtime resource IDs use query parameters on
exported detail pages. Private source and hidden judge artifacts never become
public object-storage URLs.

## Workspace routes

| Route                                                               | Responsibility                                                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `/dashboard`                                                        | Combined learning/profile/recommendation entry points, with existing CF and collaboration context |
| `/problems`                                                         | Authenticated published platform bank, search/tag/difficulty and pagination                       |
| `/problems/detail?problemId=…&problemVersionId=…`                   | Current or immutable historical statement, samples, provenance, capabilities and editor           |
| `/submissions`                                                      | Personal platform submissions with judging/date/problem filters                                   |
| `/submissions/detail?submissionId=…`                                | Independent judge and analysis states, private source and tool evidence                           |
| `/training`                                                         | Personal platform/external plans and actual training projections                                  |
| `/training/detail?trainingRecordId=…`                               | Current backend-owned attempt/acceptance/completion and attribution                               |
| `/learning-profile`                                                 | Four-window combined learning profile, history/snapshot and rebuild job                           |
| `/learning-recommendations`                                         | Mixed/source-specific recommendations, explicit generation and frozen batches                     |
| `/profile`, `/practice`, `/data`, `/accounts/**`                    | Existing CF user/account profiles, recommendation and data behavior                               |
| `/teams/**`, `/coach/**`, `/analysis`, `/privacy`, `/notifications` | Existing CF-only collaboration/report and privacy boundaries                                      |

Problem reads require a session, including COACH/ADMIN users without STUDENT.
Personal writes/readbacks require STUDENT. Platform training and combined
learning views do not require a CF binding.

## Identity, source and operation boundaries

IDs remain decimal strings or UUIDs. Problem identity contains source, platform
and problemId; immutable version is additionally required for platform statements,
editor drafts and submissions. A platform problem and CF problem with the same
numeric ID remain separate records. Training deduplication excludes version.

Drafts are temporary private query-cache data partitioned by publicId, complete
ProblemRef and languageId. Logout/session expiration clears private caches.
Source is submitted unchanged, with a 262144-byte UTF-8 limit and whitespace-only
validation. The HTTP write-body budget is separately 2 MiB because JSON escaping
can increase its encoded size. Static-analysis GET results may be much larger.

New writes use UUID Idempotency-Key. Uncertain retries preserve the operation's
exact payload and key; payload edits create a new operation. Version/language
conflicts retain source and require explicit resubmission after refresh.
Operation keys use native randomUUID when available and cryptographic
getRandomValues with UUID v4 bits on ordinary HTTP development origins. Both
V0.2 operations and retained CF recommendation generation use this helper;
authentication and cookie security settings remain independent.

Judge, static analysis and learning-profile jobs have different status enums.
Judging is visible before analysis completes. IE represents infrastructure
failure; cancellation does not mean an incorrect solution. Analysis retries
change analysisId, so revisions are compared only within their task identity.
The backend retains usable code-quality evidence during retries. Synthesis stays
NOT_REQUESTED under this release and has no execution endpoint.

Polling uses short reads, pauses on hidden pages, immediately refreshes on resume,
and backs off network failures to 30 seconds. Retryable locally failed dispatches
with no judge task reconcile at 30 seconds. No polling error repeats a POST.

Automatic profile rebuilds expose no public job ID. Latest-profile views therefore
reconcile stale results with GETs for up to 60 seconds per attempt. A source-change
signal also permits bounded reads while the first profile is still null. Fresh
results stop polling; historical snapshots never poll. Refresh starts a new read
attempt, and the existing explicit rebuild action remains available when services
take longer or fail. CF bind/unbind/sync and usable judge/analysis changes invalidate
combined training, profile and recommendation projections. Recommendation batch
completion flags can refresh while their rank, problem and reason remain frozen.

The six ability axes remain training familiarity. Code quality is separate.
Difficulty distributions preserve CF_RATING/PLATFORM_RATING/UNRATED buckets;
numeric platform difficulty is not interchangeable with CF rating. Recommendation
rank, reason, score and attribution are supplied by the backend. External
navigation creates a plan only; synchronized real CF results determine completion.

## Coding workspace

The platform detail route uses a unified adjustable statement/editor surface.
CodeMirror 6 is bundled in local production assets, with C/C++ syntax,
line numbers, search/replace, undo/redo, font sizing and wrapping. No CDN or editor
worker host is required. A plain text mode and an editor-load failure boundary
retain exact private source and associated validation. Tab leaves the editor;
search labels follow the existing locale dictionary.

Changing compiler starts a fresh editor document with that compiler's private
draft. This prevents queued editor input from mixing two compiler documents.
Editor font, wrapping and plain text preferences remain outside that document;
undo history resets when switching compiler. Wrapped controls can grow and scroll
at 200% text sizing while the code canvas retains usable height.

CodeMirror is the mature Monaco equivalent selected for this static-export
workspace. Its modular editor and C/C++ language package fit the existing
capabilities without adding Monaco worker hosting. The wrapper, C/C++ language,
commands, search, language-extension and highlighting packages are direct
dependencies because the workspace imports their APIs, including an accessible
syntax palette. The React wrapper renders only on the client; shared editor extensions
also include core editor code in the problem route's initial bundle. Other compiler
families remain editable without misleading C++
highlighting. Source download preserves the exact text; editor preferences and
temporary drafts do not become browser-persisted private source.

The statement pane keeps structured input/output specifications, samples and
provenance. Pointer and Arrow/Home/End controls resize the split and sample
console; Enter collapses a pane and transfers focus to a surviving control.
The console maximum responds to actual available space so submission actions
remain reachable. Mobile panes stack, and advanced catalog/date filters expand
without replacing their existing validated filter contracts.

Sample inputs and expected outputs are problem data, not executed results.
Run is disabled with an unavailable explanation; custom execution and actual
output are not fabricated. Submit uses the existing capability, version,
idempotency, draft and session boundaries above. Judge results and independent
analysis continue on the submission detail route.

## Legacy specification discrepancies

The V0.2 documents promise unchanged V0.12 semantics but omit team-recommendation
audience from requests and response DTOs. Existing V0.12 behavior isolates
MEMBER and COACH batches, including owner authorization and private coach data.
The frontend preserves that established boundary pending an explicit backend
contract clarification. It does not silently remove audience or expose one
audience's results to another. New V0.2 personal learning endpoints use only their
documented request fields.

V0.2's copied report type allows a nullable recent-training period start, while
its database reference and V0.12 require a frozen 30-day report period. Existing
report semantics retain the required period start. V0.2 also describes nullable
team PATCH fields differently from the current established clearing wire. These
differences require read-only backend evidence and owner clarification before
changing working legacy behavior. Added activeMemberCount and nullable shared
member learning results can be accepted compatibly without changing old results.

## Verification boundary

Use `pnpm dev:mock` or a built `pnpm preview:offline` for development and browser
review. Those commands own a synthetic loopback backend and override live backend
settings. E2E owns ports 3100/3210; stop previews before E2E. Never build while
Next development is running because they share `.next` outputs. Storybook uses
synthetic fixtures and production components/tokens.

Select a V0.2 HTTP preset with, for example,
`MOCK_SCENARIO=v02-new-learner pnpm preview:offline` after building:

| Presets                                                                                                                   | Evidence                                                                          |
| ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `v02-new-learner`, `v02-pure-platform`                                                                                    | No CF binding; empty or populated platform learning                               |
| `v02-all-verdicts`, `v02-local-failed`, `v02-cancelled`                                                                   | Judge outcomes and infrastructure/cancellation recovery                           |
| `v02-analysis-partial`, `v02-analysis-failed`, `v02-analysis-skipped`, `v02-analysis-delayed`, `v02-analysis-unavailable` | Independent analysis lifecycle and capability states                              |
| `v02-timeout-replay`, `v02-version-conflict`                                                                              | Uncertain-write replay and explicit version recovery                              |
| `v02-zero`, `v02-stale`, `v02-empty-candidates`, `v02-historical-rating`                                                  | Insufficient/stale learning evidence, empty recommendations and historical rating |
| `v02-coach-only`, `v02-admin`                                                                                             | Authenticated bank reads with personal STUDENT gates                              |
| `v02-unsafe-statement`                                                                                                    | Dedicated unsafe-Markdown fixture; normal statements remain clean                 |

The full offline HTTP backend owns synthetic judge, analysis, source-event and
profile lifecycles. Storybook uses public presentation fixtures and a separate
browser-safe recommendation/training transport; its success stories await actual
populated data. It does not execute real judge/tool services.

Synthetic tests verify the frontend contract, transitions and display behavior.
They cannot prove real sandbox verdicts, actual Lizard/clang-tidy/Infer/CPD output,
backend callback ordering/recovery, or four-container restart behavior. Real
integration requires available V0.2 backend/judge/algorithm services and the
documented deployment environment. Production release remains a separate action;
the delivery PR must stay unmerged until approved.

Validation results and remaining service dependencies are recorded in the delivery
plan and GitHub milestone as evidence becomes available.
