# codeStartrack V0.1 Page Structure

## Current read-only execution decisions

The user's later gateway/read-only instructions govern current implementation. Browser API requests go only to the Next.js application: `GET /api/training/profile` and `GET /api/training/recommendation` forward server-side to `GET /api/users/1/profile` and `GET /api/users/1/recommendations?limit=1`. Use one `DEMO_USER_ID = 1` and server-only runtime `BACKEND_BASE_URL`; never expose the backend through `NEXT_PUBLIC_*`. No POST, PUT, PATCH, DELETE, HEAD or OPTIONS may reach the live backend. E3/E4/E5 and the binding/synchronization flows described below remain deferred specifications, not current executable work.

P-01–P-05 are [resolved for this read-only slice](product-requirements.md#approved-v01-product-decisions): `/` links to the existing Demo `/dashboard`; retry only a failed GET; visibly disclose early placeholder recommendations; zh-CN default/en on the same routes, external problems in a new tab; white/neutral-first colors with blue only as an accent. The dashboard is a planned destination, not an already implemented scaffold route. No product UI is added by V01-01.

## Scope and route model

Milestone: **V0.1 — Unified Training Profile & Recommendation (Codeforces First)**. [The current rewrite instruction](../../prompts/v01-doc-rewrite.md) takes precedence over the former Demo V2 route model in the unchanged repository instructions and product plan. See [requirements](product-requirements.md), [API contract](api-contract.md), and [design direction](design-system.md).

```text
/
  Read-only Demo entry
/dashboard
  Unified training profile + one primary recommendation
```

These are page specifications, not implemented routes. The [same-platform account update](../../prompts/v01-doc-update-multiple-same-platform-accounts.md) approves one learner with zero or more connected external accounts, including multiple accounts on the same platform. Each real account has its own `account_id` and independent synchronization; all successfully imported data feeds one backend-normalized/deduplicated dataset, one unified profile, and one recommendation experience. Source/account provenance remains visible without creating account-specific dashboards or platform modes.

V0.1 uses the temporary `DEMO_USER_ID = 1` and environment-configured backend URL server-only runtime `BACKEND_BASE_URL`. Identity is resolved for this Demo; authentication/provisioning work is not reopened. Codeforces is the only available connector, and current E3 permits at most one Codeforces account for that user. A second same-platform account is **BLOCKED_BY_API** (G-09), not a working connection action. Account-list/status recovery remains missing despite the known Demo user ID.

A future connector extends the connected-account surface and backend ingestion. It does not require another dashboard or a different learner identity, goal, or product mode. V0.1 does not need a large navigation shell for two pages.

Keep the original dashboard state when returning from the external tab; focus/reconnect must not refetch data or claim problem completion. Link validation failures do not turn a valid card into a fabricated result.

### Connected Accounts collection: target vs current implementation

Target structure, illustrative only after backend support; these are not real records or approved fixtures:

```text
Connected Accounts
  Codeforces · account_A    Connected    account-specific sync state
  Codeforces · account_B    Connected    account-specific sync state
  + Connect another account
```

Each row conceptually holds platform, public username, connection status, account-specific sync state, last sync time when known, and per-account re-sync when supported. Repeated platform names are valid; each account's backend `account_id` distinguishes it. The username is source metadata, never a replacement for the internal learner identity.

Currently E3 can bind only one Codeforces account per user. Connect another account must remain blocked/not yet available, never usable or represented as successful. E3 provides the just-bound row and E4 the just-completed sync result; neither lists all user accounts, inspects current per-account server sync status, nor restores IDs after reload (G-02). Do not make browser-local account names into fictitious bindings.

For the target collection, keep failures and stale sync times scoped to their accounts. All successfully synchronized account data contributes to the same user analysis; a failed account sync does not imply complete refresh of every account. Backend-defined normalization/deduplication owns overlap; the browser does not merge separate learner profiles or sum raw account totals.

## Deferred binding/synchronization operation sequence

```text
IDLE → CONNECTING_ACCOUNT → SYNCING_DATA → BUILDING_PROFILE
     → LOADING_RECOMMENDATION → READY
```

| Operation                | API / completion evidence                                                                             | Failure boundary                                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `IDLE`                   | Use `DEMO_USER_ID = 1` and server-only runtime `BACKEND_BASE_URL`; no active request.                 | Identity is resolved for this Demo. Missing external-account context after reload is G-02, not a need to create another user.        |
| `CONNECTING_ACCOUNT`     | E3 binds the first account for user 1 and returns 201 with its `account_id`.                          | Keep the existing 409 behavior; Connect another account remains **BLOCKED_BY_API** (G-09).                                           |
| `SYNCING_DATA`           | E4 returns 200 with `status = "success"`, counts and `synced_at`.                                     | Preserve the connected account; a transport timeout does not prove server-side cancellation.                                         |
| `BUILDING_PROFILE`       | E1 returns the computed `ProfileResponse`. This is a GET read, not a documented background-build job. | Show profile unavailable; do not infer a polling job or repeatedly bind/sync to manufacture a profile.                               |
| `LOADING_RECOMMENDATION` | E2 returns its recommendation batch. The backend may reuse it.                                        | Keep a successful profile usable; handle no candidate separately from a request failure when the contract supports that distinction. |
| `READY`                  | The profile and a usable recommendation have loaded successfully.                                     | Do not use READY to imply validated ability scores, a mature algorithm, or completion of external practice.                          |

Operation labels do not need to become URLs or backend statuses. Account not found, account conflict, external platform unavailable, synchronization failed, profile unavailable, and recommendation unavailable are frontend error categories; the current repeated `account_not_found` examples do not establish an identifier for every category.

## Future connector extension

Additional same-platform accounts, after G-09 is resolved, and future connectors extend the same account collection with provenance, connection status and independent per-account sync context. Their data feeds the existing user-level profile and recommendation pages. The recommendation component keeps source labels, external IDs and URLs, without adding platform modes or changing the learner model. No future integration is enabled by this document; if shown at all, unsupported connectors must be secondary and explicitly labeled Coming soon.

## Future / Post-V0.1

The earlier `/training`, `/history`, `/profile`, `/problem/[id]`, `/coach`, `/coach/students`, and `/coach/student/[id]` routes are deferred. They do not appear in V0.1 navigation, state transitions or acceptance checks. Internal editing, Run Sample, judging/submission history, progressive Agent help, teams and role switching require later approved scope and contracts.
