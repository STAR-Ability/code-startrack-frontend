# CodeStartrack / 码练星轨 V0.12 前端需要知道的数据库 / 数据模型

> 本文只描述 Frontend 需要理解的 V0.12 业务关系与页面状态。数据库表名、FK、索引、Algorithm 内部 DTO 都不是前端依赖；具体字段以《V0.12 前端 API 文档》为唯一公开契约。

## 1. 服务边界不变

```text
Browser → Frontend:80 → /api/v1/** → Backend:8081
                                    ├→ PostgreSQL
                                    └→ Algorithm:8000
```

Frontend：

- 不连接数据库。
- 不调用 Algorithm。
- 不调用 Codeforces API。
- 不依据数据库表结构实现权限。
- 不计算个人/团队画像公式。

## 2. V0.12 核心关系图

```text
User
 ├─ roles[]
 │   ├─ STUDENT（注册默认）
 │   └─ COACH（额外角色，可同时存在）
 │
 ├─ OjAccount A ─┐
 ├─ OjAccount B ─┼→ UserAnalysis（多 CF 汇总）→ PersonalReport[]
 └─ OjAccount N ─┘

User
 └─ TeamMember[]
      ├─ Team A
      ├─ Team B
      └─ Team C

Team
 ├─ one OWNER
 ├─ many MEMBER
 ├─ JoinApplication[]
 ├─ TeamInvitation[]
 ├─ TeamAnalysis
 └─ TeamRecommendation[]

User
 ├─ PrivacySettings
 └─ Notification[]
```

## 3. 系统角色与团队角色必须区分

### 系统 Role

```text
STUDENT
COACH
ADMIN
```

来自 `UserDto.roles`。

### 团队内 Role

```text
OWNER
MEMBER
```

来自 `TeamMemberDto.role`。

不要混淆：

- 用户有 COACH 不代表他对所有团队都有管理权。
- 只有 `TeamDetail.canManage=true` / `myMembershipRole=OWNER` 才能管理具体团队。
- 一个 COACH 可以是 A 团 OWNER，同时只是 B 团 MEMBER。
- COACH 始终保留 STUDENT 功能。

## 4. Team 稳定 ID

| 字段 | 类型 | 前端语义 |
|---|---|---|
| `teamId` | UUID string | 团队稳定 ID，路由/cache 使用 |
| `membershipId` | UUID string | 一次加入关系历史 ID |
| `applicationId` | UUID string | 一次加入申请 |
| `invitationId` | UUID string | 一次邀请 |
| `notificationId` | UUID string | 一条通知 |
| `snapshotId` | UUID string | 用户/团队分析快照 |
| `reportId` | UUID string | 个人报告 |
| `jobId` | UUID string | AI 异步任务 |

这些 ID 都是不透明值，不拼接业务含义、不做算术。`TeamSummary.memberCount` 始终表示当前 ACTIVE membership 数；DISSOLVED 团队为 0，不与历史 membership 总数混用。

## 5. TeamMember 生命周期

同一用户可多次加入同一团队，但前端一次只会看到一个 ACTIVE membership。

```text
加入
 ↓
ACTIVE
 ├─ 主动退出 → LEFT
 └─ Owner 移除 → REMOVED
```

重新加入会产生新的 membershipId。

OWNER：

- 在 ACTIVE/ARCHIVED 团队中必须保持 ACTIVE。
- 不能普通 leave。
- 转让后旧 OWNER 变 MEMBER，新 OWNER 变 OWNER。
- 团队 DISSOLVED 时最终 OWNER membership 会与其他成员一起结束为 REMOVED，仅作为历史保留 OWNER 角色。

## 6. 加入申请状态机

```text
PENDING
 ├─ APPROVED
 ├─ REJECTED
 └─ CANCELLED
```

终态不可再次操作。

前端保存的申请对象以 API 返回为准，不要在本地先把 PENDING 改 APPROVED 后假设 membership 已创建；mutation 成功后刷新 application + team membership。

## 7. 邀请状态机

```text
PENDING
 ├─ ACCEPTED
 ├─ REJECTED
 ├─ EXPIRED
 └─ CANCELLED
```

邀请按邮箱创建：

- 已注册用户：站内可见。
- 未注册用户：注册并验证相同邮箱后，Backend 自动关联；Frontend 不需要做“邮箱匹配逻辑”。
- Owner 侧使用 `emailDeliveryStatus` 判断邮件是否 SENT/FAILED；FAILED 可重发，不等于 invitation 已取消。

## 8. Team 状态

```text
ACTIVE
 ↕
ARCHIVED

ACTIVE/ARCHIVED
 ↓
DISSOLVED（终态）
```

页面语义：

- ACTIVE：可申请/邀请/管理成员。
- ARCHIVED：只读为主，不接受新申请/邀请。
- DISSOLVED：历史只读，不再恢复。

V0.12 的 `/teams/search` 只返回 ACTIVE；“我的团队”只表示当前 ACTIVE membership 所在的 ACTIVE/ARCHIVED 团队，不承担历史团队归档页职责。

## 9. V0.11 account 分析 与 V0.12 user 分析

这是前端最容易混淆的地方。

### Account-level（V0.11）

```text
selectedAccountId = A
→ /oj-accounts/A/analysis/**
```

表示某一个 Codeforces 绑定。

### User-level（V0.12）

```text
当前登录 User
→ 所有未解绑 ACTIVE/INVALID CF 绑定（每个都至少有一次完整成功同步）
→ 跨账号去重
→ /me/analysis/**
```

表示“码练星轨用户统一画像”。

INVALID 账号如果过去存在完整成功同步，会使用最后成功数据参与聚合，并使用户画像标记 `stale=true`；从未成功同步的未解绑账号不会被静默忽略，而会让新的用户级聚合等待/失败为 source-not-ready。

因此：

- 平台账号页：保留 selectedAccountId。
- 个人画像页：不用 selectedAccountId。
- 学生主页：不用 selectedAccountId。
- 报告页：不用 selectedAccountId。

## 10. 用户级 Rating 展示

统一画像中的：

```text
currentRating = 绑定账号 currentRating 的最大值
maxRating     = 绑定账号 maxRating 的最大值
```

所以前端文案必须准确：

- “最高当前 Rating”
- “最高历史 Rating”

并使用 `ratingAccounts[]` 展示各账号独立 Rating。

不要写“合并 Rating”。

## 11. UserAnalysis 状态

```text
null
→ 尚未生成

stale=false
→ 当前可用

stale=true
→ 可展示旧结果，但当前 CF 数据已变化
```

stale 不是错误。页面可继续展示旧结果并提示后台正在/需要重建。

## 12. PersonalReport 是历史冻结对象

```text
PersonalReport
 ├─ statisticsSnapshot
 ├─ profileSnapshot
 ├─ recentTrainingSnapshot
 └─ content
```

查看旧报告时：

- 使用报告自己的 snapshot。
- `recentTrainingSnapshot` 固定来自 30D 画像，因此 `period.start` 必须有值；ALL 快照才允许 start=null。
- 不用当前最新 `/me/analysis/latest` 替换当时数据。

这样历史报告不会随算法/数据变化“变脸”。

## 13. PrivacySettings 模型

四类数据分开授权：

```text
basicTraining
abilityProfile
detailedSubmissions
analysisReport
```

每类都取：

```text
PRIVATE
TEAM_COACH
TEAM_MEMBER
PUBLIC
```

Frontend 只负责编辑和展示。

Backend 才负责决定某 viewer 是否真的符合 TEAM_COACH/TEAM_MEMBER。

## 14. TeamMember.dataAccess

成员列表返回当前 viewer 对每个成员的可访问能力：

```ts
dataAccess: {
  basicTraining: boolean;
  abilityProfile: boolean;
  detailedSubmissions: boolean;
  analysisReport: boolean;
}
```

这个对象是 UI 最直接的权限依据，并且它是**针对当前 TeamMemberDto 所属 teamId 计算的**；前端不得把 A 团成员卡片的 dataAccess 复用到 B 团。

但它不是安全边界：

- dataAccess=false → 不显示入口。
- dataAccess=true → 可以请求。
- Backend 仍会在请求时重新检查关系和隐私。

## 15. Team Analysis 的 audience

同一个 Team 可能存在两份最新分析：

```text
COACH audience
MEMBER audience
```

原因：成员可能只允许教练查看画像。

Frontend 不传 audience：

```text
GET /teams/{teamId}/analysis/latest
```

Backend 根据当前用户自动选择。

因此不同用户看同一个团队的 includedMemberCount/score 可能不同，这是正常行为，不是缓存 bug。

## 16. Team Analysis 样本量

必须同时展示并正确解释四种样本量：

```text
memberCount           当前 ACTIVE 成员总数
includedMemberCount   abilityProfile 样本数
trainingMemberCount   basicTraining 活动样本数
levelMemberCount      basicTraining 中有可用等级基数的样本数
excludedMemberCount   memberCount - includedMemberCount
```

`targetRating == null` 当且仅当 `levelMemberCount == 0`；即使 trainingMemberCount>0，也可能因为所有成员都没有 averageSolvedDifficulty/currentRating 而无法生成目标难度。

尤其：

```text
includedMemberCount = 0
```

含义是“当前 audience 没有可用于分析的数据”，不是团队能力真的等于 0。

## 17. Team Recommendation 的隐私语义

团队推荐与 TeamAnalysis 一样区分 `COACH` / `MEMBER` audience，防止把只授权给教练的数据通过推荐结果间接泄露给普通成员。

- `MEMBER` 批次：普通 ACTIVE member 可读；只能基于 MEMBER team analysis，coverage 只使用 `detailedSubmissions=TEAM_MEMBER/PUBLIC` 且数据就绪的成员。
- `COACH` 批次：仅 OWNER 可读；基于 COACH team analysis，coverage 使用 OWNER 对成员实际拥有 detailedSubmissions 访问权的数据。

公开 DTO 仍只返回题目、团队级分数和原因；不返回 memberSolvedCount、eligibleMemberCount，也不返回“哪些成员做过”。同一 audience 内，coverage 集合与 abilityProfile 的 includedMember 集合来自**独立隐私设置**，所以人数可能更小、相等或更大。Frontend 不应通过成员提交接口重建或展示该集合，也不得把 COACH 批次缓存/展示给普通成员。

## 18. Notification 与业务对象的关系

Notification 不是业务状态源。

例如收到：

```text
JOIN_APPLICATION_APPROVED
```

点击后仍应请求：

```text
/me/team-applications
/teams/{teamId}
```

不要只根据 notification.body 把本地 application 改为 APPROVED。P2 邮件通知同样只是 delivery channel，不是新的业务状态源；邮件内容不能替代 API 查询。

## 19. AI Job 模型

```text
QUEUED
 ↓
RUNNING
 ├─ SUCCESS → resultId
 └─ FAILED  → errors[]
```

AI job 只用于：

```text
USER_ANALYSIS
PERSONAL_REPORT
TEAM_ANALYSIS
TEAM_RECOMMENDATION
```

CF 同步仍用 V0.11 `SyncJobDto`，不要混成一个前端类型。

## 21. 前端状态分区

建议不要使用一个全局 selectedTeamId/selectedAccountId 驱动所有页面。

```text
Auth State
  user/publicId/roles

OJ Account State
  selectedAccountId   // 仅账号详情类页面

Team Route State
  teamId              // 由路由决定

User Aggregate State
  不依赖 accountId

Notification State
  unreadCount
```

## 22. Cache 隔离

### 账号级

```text
[publicId, accountId, ...]
```

### 用户级

```text
[publicId, "user-analysis", ...]
[publicId, "reports", ...]
```

### 团队级

```text
[publicId, teamId, resource, ...]
```

必须保留 publicId，因为同浏览器退出再登录不同账号时不能复用私人 cache。

## 23. 前端不应持久化的字段

不要把以下作为 localStorage 的长期授权事实：

- `canManage`
- `dataAccess`
- roles
- invitation/application PENDING 状态
- unreadCount

它们都可能变化；刷新应用时以 Backend 为准。

可以持久化：

- UI theme
- locale
- selectedAccountId 偏好（需按 publicId 分区）
- 非敏感布局偏好

## 24. Mock 的关系一致性

Mock 不能随便拼对象，至少满足：

- TeamSummary.owner 必须与 TeamDetail owner 一致。
- OWNER 必须出现在 active members。
- APPROVED application 对应用户应能出现在 members。
- ACCEPTED invitation 对应用户应能出现在 members。
- COACH 用户仍有 STUDENT。
- includedMemberCount + excludedMemberCount = memberCount（当前文档约定；若 owner 无画像也算 excluded）。
- levelMemberCount <= trainingMemberCount <= memberCount；levelMemberCount=0 时 targetRating=null，反之 targetRating 非 null。
- TeamRecommendation 不公开逐成员覆盖计数字段；coverage 样本数与 includedMemberCount 无大小关系假设；batch.audience 必须等于 analysis snapshot audience，普通成员只能读取 MEMBER batch。
- report.analysisSnapshotId 应指向当时的 user ALL snapshot。

## 25. 前端验收思维模型

只要 Frontend 开发者遵循以下原则，就不需要知道数据库表：

1. `/me` 决定系统角色入口。
2. TeamDetail 决定具体团队权限。
3. `dataAccess` 决定成员数据入口。
4. Backend 403/409 是最终裁决。
5. selectedAccountId 只影响 account 级页面。
6. `/me/analysis` 是多账号统一画像。
7. AI job 与 CF sync job 分开轮询。
8. Team analysis audience 由 Backend 自动选择。
9. 历史 report 使用冻结 snapshot。
10. 所有业务 mutation 后按对象精确 invalidate cache。
