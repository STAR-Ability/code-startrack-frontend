## Hard live network constraint

**The live backend at `http://116.62.214.151:8080` is READ-ONLY. Only GET requests may be sent to it.** This is a task constraint, not a UI preference or an environment toggle.

It applies to every browser/server fetch, Server Component, route handler, Server Action, API client, curl/shell command, setup script, test, Playwright run and debugging utility. Do not send POST/PUT/PATCH/DELETE, HEAD or OPTIONS probes. Do not call mutation endpoints using GET. Do not bind, synchronize, initialize, reset, seed, repair or modify live data. In particular, E3 `/api/accounts`, E4 `/api/accounts/{accountId}/sync` and E5 `/api/problems/sync/{platform}` must have no active caller in this Issue.


If necessary, API documentation may be inspected with `GET /v3/api-docs`; it is not an application feature. Do not enumerate other users, endpoints or accounts.

## Exact scope

### 1. Configuration

- Add one clearly named, replaceable configuration export for `DEMO_USER_ID = 1`. The gateway always selects it server-side; do not let browser input select another user. Keep external `account_id` distinct. Tests should prove user-ID override attempts cannot change upstream paths.
- Read the base URL exclusively from server-only runtime `BACKEND_BASE_URL`. Validate it when a gateway read is requested: require a usable absolute HTTP(S) backend origin, reject embedded credentials or ambiguous path/query/fragment configuration, and handle a trailing slash consistently. There must be no request or configuration-triggered application crash merely from importing a module or building without the variable. Restarting the same built server with a different value must retarget upstream reads.
- Treat missing/invalid configuration as an explicit local error before invoking transport. Do not fall back to the live origin, localhost, a relative endpoint, or fixture data.
- Create `.env.example` with the empty variable and add only the necessary `.gitignore` exception for that example. Keep `.env.local`, other real env files and secrets ignored. Document runtime server configuration and read-only setup in a focused existing setup section. The later Compose `.env` must explicitly inject the variable into the container; it is separate from Next.js local `.env.local`. No source-code or image default may contain the live host.

### 2. Server-only client and narrow Next.js gateway

- Centralize backend request logic under `src/lib/api/`, protected by `server-only`. Keep any shared DTO/error/schema modules free of server configuration so later browser-safe same-origin accessors can consume them without importing the backend client. Do not create a general service framework.
- Add two explicit Node.js Route Handlers under `src/app/api/training/`: frontend `GET /api/training/profile` maps only to upstream `GET /api/users/1/profile`; frontend `GET /api/training/recommendation` maps only to upstream `GET /api/users/1/recommendations?limit=1`. These are frontend-owned APIs, not new backend endpoints or product pages. Fix identity/limit from configuration; reject unexpected query/body input.
- Expose private domain accessors for E1/E2 only. No catch-all proxy, arbitrary destination/path/user/limit parameter, open redirect, browser-config endpoint, forwarding of `/v3/api-docs`, or mapping to E3/E4/E5.
- Browser API clients will use only the two relative same-origin URLs. Do not forward inbound cookies, authorization, arbitrary headers or method overrides. The explicit external problem CTA remains normal user navigation and is not a backend fetch.
- Use an internal GET-only transport with no caller-controlled method/body or arbitrary endpoint escape hatch. Upstream requests have no body, use `Accept: application/json`, omit credentials and do not forward browser headers. Server calls do not require backend CORS configuration.
- Keep handlers request-time and uncached, with no-store upstream requests/responses. Do not opt into static generation or cache backend responses through Next.js. Do not follow redirects; use a bounded timeout/AbortSignal and map failures safely. No automatic retries, polling, background refresh, module-import fetch, build-time prefetch or setup reads.
- Unsupported methods return a local 405 with zero upstream calls; explicitly handle HEAD locally because Next.js otherwise auto-implements it by calling GET. OPTIONS may return a local framework response, but must never call upstream. Never implement forwarding POST/PUT/PATCH/DELETE or method-override behavior. Negative method tests target only an isolated local gateway/stub.
- Accept an AbortSignal where useful and keep the transport testable with a stub. There is no need to add QueryClientProvider or hooks before the dashboard consumer exists.

### 3. Runtime validation

- Parse external data as `unknown` and use the installed Zod dependency. Preserve documented wire field names; infer usable types from schemas instead of duplicating interfaces.
- E1 consumes `userId`, `totalSolved`, `averageDifficulty`, `maxDifficulty`, `recentActivity.last_7_days`, `recentActivity.last_30_days` and `updatedAt`. Validate values needed to render truthful metrics. Missing/invalid required metrics must yield an explicit payload failure, never zero. Zero numeric activity itself is valid. Do not convert `skills` into measured ability or require it as a UI dependency.
- E2 consumes `userId`, `recommendations`, `generatedAt` and the displayed problem metadata: internal/source IDs, platform, title, difficulty, tags, URL and reason. Handle an empty recommendations array, empty title, nullable difficulty and empty tags without inventing values. Permit absent display metadata where needed for the documented defensive UI states, retaining its absence rather than manufacturing a value; explain this tolerance as frontend policy, not proof that the backend guarantees omission.
- Preserve a missing/invalid external URL as an unusable action for the later UI; never construct a URL from platform/ID. A later CTA may use only an absolute HTTP(S) supplied URL. Do not turn `score` into confidence, ranking guarantees or personal analysis.
- Validate IDs as safe integers under the documented numeric contract and reject unsafe values rather than silently rounding or assuming an undocumented string-ID protocol. Profile/recommendation user identity must match the requested learner. Keep timestamps distinct and validate usable date-time values without assuming an undocumented precision limit.
- Accept unrelated additional response fields where harmless; do not freeze the entire schema to one successful sample. If a real payload contradicts the documented consumed fields, report the exact gap and fail safely instead of silently rewriting API guarantees.

### 4. Errors

- Preserve available upstream HTTP status and documented `{ error, message }` semantics for internal classification, without inventing backend `code`, `details` or identifiers. The browser receives a separate, documented frontend-owned normalized error representation containing safe operation/category/status and a safe machine identifier when available; never serialize the raw upstream message/body, URL, stack or environment.
- Distinguish configuration, transport/abort, non-2xx HTTP, invalid JSON and response-schema failures in a small shared frontend error model. These frontend categories are not wire codes.
- A 404 does not by itself prove no binding/no user/no candidates. The docs reuse `account_not_found` examples; do not infer every recovery branch from them.
- Handle non-JSON/empty error bodies without losing available upstream status. Define the gateway HTTP mapping: invalid local input 400, unsupported method 405, configuration failure 500, upstream transport/invalid-payload failure 502 and timeout 504; preserve non-2xx upstream status when appropriate without leaking its body. These are frontend boundary semantics, not new backend guarantees. No raw backend response or identifying payload should be logged or transformed into reusable UI text. Localized presentation is a later Issue.

### 5. Focused regression coverage and review

Use existing Vitest and colocated `src/**/*.test.{ts,tsx}` conventions for unit tests, and the existing Playwright harness for focused HTTP tests of actual Next.js Route Handler dispatch. Stub transport/environment for unit tests and restore them afterward. For integration, start a controlled local synthetic upstream and inject its URL into the Next.js server at runtime. Do not save live learner payloads into fixtures; browser routing mocks alone cannot intercept server-to-server requests.

Cover exact E1/E2 paths, fixed user 1/limit=1, GET/no body, no header/credential/redirect passthrough, configuration failures with zero upstream calls, consumed-field parsing, valid zero/empty/nullable values, user mismatch, unsafe IDs, malformed payloads, HTTP/abort/network/timeout errors and safe HTTP serialization. Test arbitrary URL/path/user/limit/method-override attempts and local POST/PUT/PATCH/DELETE/HEAD/OPTIONS dispatch, asserting zero upstream calls. Do not send prohibited requests to the live backend to test rejection.

Build without a backend value; run the same built server against two controlled runtime upstream URLs and verify the destination changes without rebuilding client JavaScript. Check delivered browser assets/HTML/error bodies for backend-host leakage and ensure a Client Component cannot import server-only modules. Browser API requests must target only Next.js. Keep full container/image testing in V01-08 and live verification in V01-09.
